# Sensors Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `[[sensor]]` beam breaks, distance sensors and REV Color Sensor V3s that see game pieces, read by robot code
and by the Test tab.

**Architecture:** a new `scrimmage/sensors/` package parses `[[sensor]]`, resolves each to a robot body and a ray in
its frame, and each physics step casts one `mj_ray` per sensor (pieces only, or anything but the robot). It hands
readings to the HAL as DIO, AI or the color sensor's SimDevice, and to the Test tab's Watch.

**Tech Stack:** Python 3.11+, MuJoCo (`mj_ray`), HALSim WebSocket, REVLib 2026 ColorSensorV3 (SimDevice), Blockly,
pytest.

**Spec:** docs/superpowers/specs/2026-11-05-sensors-design.md

## Global Constraints

- Robots without `[[sensor]]` are byte-identical (`tests/test_range_ledger_golden.py`).
- **Ray cost:** one `mj_ray` per sensor per physics step, and only when the robot has sensors. A sensor never sees
  its own robot's geoms.
- **Pieces** are the `ball.<i>` bodies, the same for balls, discs and rigid pieces.
- **The color sensor:** its SimDevice is `REV Color Sensor V3[<port>,82]`, with values `Red`, `Green`, `Blue`, `IR`
  and `Proximity`. The I2C port is 0 for onboard and 1 for MXP, as RobotPy 2026.2.2 showed with MXP giving
  `[1,82]`.
- **Wording and tests:** American spellings and plain words. Never run `uv run` in the repo root; use
  `.venv/bin/python -m pytest`, serially.

## Review Focus

1. **A beam whose two ends are inside the same robot geom** (a beam drawn through a part). It still sees pieces
   crossing it, because it ignores the robot, and never reads broken by itself. Test: Task 1.
2. **A piece resting exactly on the beam's end point.** It reads broken, with no flicker step to step at rest. Test:
   Task 1.
3. **Two sensors on the same DIO channel, or a sensor on a shooter beam break's DIO:** an error naming both. Test:
   Task 2.
4. **A color sensor with nothing in front:** low values and "sees nothing", not the color of the carpet or the
   robot. Test: Task 1.
5. **A sensor on a body the robot doesn't have:** an error listing the robot's bodies. Test: Task 1.

### Task 1: Sensors in the world

**Files:**
- Create: `scrimmage/sensors/__init__.py`, `scrimmage/sensors/spec.py` (parse `[[sensor]]`), `scrimmage/sensors/runtime.py`
- Modify: `scrimmage/world.py` (build, `step` reading after `mj_step`, `reset`), and piece colors (`color` on piece
  kinds and range balls: find where presets give the drawn rgba)
- Test: `tests/test_sensors.py`

**Interfaces:**
- **`[[sensor]]` keys:**
  - all kinds: `name`, `kind` ("beam" | "distance" | "color"), `body` ("<inst>.<body>");
  - beam: `from`, `to` (m, in the body's frame; `_in` forms too);
  - distance and color: `at`, `toward` (a direction), `max_range` (m; default 2.0 for distance, 0.10 for color),
    `sees` ("pieces" | "anything"; default "pieces");
  - outputs: `dio`, `analog`, `i2c` ("onboard" | "mxp"), `active_low` (bool, default true), `volts_per_m` (0.977),
    `threshold` (m; default `max_range`/2).
- **`SensorRuntime(world, specs)`:**
  - `update(data)` runs after each `mj_step`;
  - `reading(name) -> Reading(on: bool, distance: float | None, color: (r, g, b) | None, color_name: str | None)`;
  - `sensor_updates() -> list[Update]`, added to `World.sensor_updates`;
  - `world.sensors` is None when there are none.
- **Rays:**
  - `mj_ray(m, d, pnt, vec, geomgroup, flg_static, bodyexclude, geomid)`, with exclusion of the robot's root tree.
    "pieces" keeps hits on `ball.*` bodies only: cast against piece geoms by repeating the cast past non-piece hits,
    or use a geom group if pieces have one. Pick one and comment why.
  - A beam is a ray from `from` toward `to` with length |to − from|.
- **Colors:** `piece_color(kind) -> (r, g, b)` from the kind's `color` key, or its drawn rgba. A named-color table of
  8 colors (red, blue, yellow, orange, green, purple, white, gray) gives `nearest_color((r, g, b)) -> str`.
- [ ] **Step 1: Write the failing tests:**
  - a beam across a stand-in intake mouth reads broken while a ball rolls through, and clear before and after;
  - Review Focus 1, 2, 4 and 5;
  - a distance sensor reads the distance to a ball 0.5 m ahead within 1 mm, and the max when nothing is in range;
  - a color sensor in front of a red piece names "red", and two kinds of different color read differently;
  - a robot without sensors has `world.sensors is None` (the golden passes).
- [ ] **Step 2–4: Implement and run** them plus `-k "world or range or golden"`. Expected: PASS.
- [ ] **Step 5: Commit:** `git commit -m "sensors: beam breaks, distance and color sensors that see game pieces"`

### Task 2: Robot code reads the sensors

**Files:**
- Modify: `scrimmage/sensors/runtime.py` (`sensor_updates`), `scrimmage/world.py` (the duplicate-device check includes
  sensors), `scrimmage/bridge.py` (if the color SimDevice needs listing, e.g. a missing-device warning)
- Test: `tests/test_sensors_hal.py`, `tests/test_sensors_robot_e2e.py`

**Interfaces:**
- **DIO:** `("DIO", "<n>", {"<>value": bool})`, following the existing `DigitalBinding`.
- **AI:** `("AI", "<n>", {">voltage": v})`, clamped to 0–5 V.
- **Color:** the color SimDevice's values, as the bridge sends other SimDevice inputs. Find how the halsim_ws client
  names a SimDevice with no type prefix (check `from_sim_device` and protocol.py; verify with a live RobotPy run, as
  sub-project 23 did for the PCM). Values: `Red`, `Green`, `Blue` and `IR` (0–2047 ints scaled from C5's
  brightness), and `Proximity` (0–2047).
- [ ] **Step 1: Write the failing tests:**

  - **Review Focus 3:** the duplicate channel error.
  - **e2e (model on tests/test_rev_py_e2e.py):** a RobotPy program reads a `DigitalInput` beam break and a
    `ColorSensorV3` (MXP) while a ball sits in front, and prints them. The printed values match: the beam reads broken
    (False when active-low), and the color sensor's red is above its blue for a red ball.
- [ ] **Step 2–4: Implement and run** them plus `-k "bridge or rev or sensors"`. Expected: PASS.

### Task 3: Sensors in the Test tab

**Files:**
- Modify: `scrimmage/blocks/program.py`, `conditions.py`, `run.py`, `palette.py`, `scrimmage/assembler/static/blocks_defs.js`
  and the replay drawing (live3d.js), and `scrimmage/assembler/view.py` (model_view gains sensors)
- Test: `tests/test_blocks_sensors.py`, plus the Test tab browser and server tests

**Interfaces:**
- **The condition** `"sensor"`: `{sensor, is: "on" | "off", sees: <color name> | None}`. `describe` reads "beam is
  on" or "color sees red".
- **Signals:** `sensor.<name>`: 0/1 for a beam, inches for a distance, the matched color index or NaN for a color.
  They are listed in `palette()["signals"]`.
- **Palette:** `palette()["sensors"]: [{name, kind}]`.
- **Problems:** an unknown sensor lists the robot's sensors, and `sees` on a non-color sensor is an error.
- **Replay:** `model_view` gains `sensors: [{name, a: [mover, pos], b: [mover, pos]}]`, using the same mover
  convention as cylinders. The replay draws a thin line, lit while on. The line's "on" comes from the run's sensor
  signal at each frame.
- **Block:** *sensor [name] is [on/off] [sees color?]*, hidden with no sensors.
- [ ] **Step 1: Write the failing tests:**
  - a stand-in spinning its intake until `wait_until sensor beam is on`, then stopping, holds the ball in the mouth;
  - the names checks and the file shape;
  - the block round-trips;
  - model_view lists the sensors.
- [ ] **Step 2–4: Implement and run** them plus `-k "blocks or browser or test_server"`. Expected: PASS.
- [ ] **Step 5: Commit:** `git commit -m "test tab: a sensor condition, sensor signals, and sensors in the replay"`
